# 修正层重构：从易朽样例到不可变源覆盖

> 状态：方案待评审（未进入实现）· 日期：2026-06-30 · 范围：版本管理 / 知识回写 / 发布门禁
>
> **已拍板决定**：待复核期间采「冻结上一已确认值 + 标记」，即*带债发布、债务可见*，而非*有待复核就阻断整次发布*（详见 §3.3、§4 Phase 4-A）。

## 1. 出发点（Why）

### 1.1 初衷与现实的偏差

知识库的初衷是三件事：**可审计、可管理、可发布**。为此系统建了四条不可变链（资料 / 构建 / 审核标注 / 发布）加一条把它们缝起来的回写链。但在「人工修正如何沉淀」这一环上，当前实现与初衷背道而驰。

用户希望：**人工修正能持久化，保证知识沉淀**。即一条被人改对的知识，下一次构建不该再让 LLM 重新推它，而应作为「冻住的事实」永远生效。

当前实现：人工修正落在 `annotation_examples`，以 **hint / override 两种模式**存在，每次构建**重新喂给 LLM 一个提示，再赌它这次听不听话**。这不是沉淀，是「每次重新打一遍官司，只是递了张小抄」。

### 1.2 三个实锤问题

**问题 A：修正被 schema 主动删除（最严重）。**

```sql
-- src/server/db.ts:193
CREATE TABLE annotation_examples (
  example_id   TEXT PRIMARY KEY,
  package_id   TEXT NOT NULL REFERENCES asset_packages(package_id)   ON DELETE CASCADE,
  component_id TEXT NOT NULL REFERENCES asset_components(component_id) ON DELETE CASCADE,  -- ☠️
  ...
)
```

人工修正外键挂在「会被重建删掉」的 `asset_components` 上，且带 `ON DELETE CASCADE`。每次 rebuild 旧 package/component 一删，**数据库自动连坐删掉沉淀的修正**。要「沉淀」，却把沉淀物拴在了最易朽的东西上。

**问题 B：寻址锚点不稳。**

修正靠 `component_id + context_hash` 匹配回组件。但 `releaseService` 自己的注释承认 **`componentId 跨构建不稳定`**（所以可信度只能按 `artifactId` 对齐）；`context_hash` 又随资料内容变化而变。一条在 build N 做的修正，凭什么落到 build N+1 的同一组件上？靠 contextHash → 资料一改就**静默失效**。

> 值得注意的是：override 在构建时**实际是按 `sourcePath` 匹配的**（`extractStage.ts:405` `annotationOverrideMatches`，用 `rel` / `page.source` 比对）。修正的天然锚点本就是**源文件路径**，只是存储时拴错了地方。

**问题 C：缺少「源漂移」状态机。**

当新 source version 进来、某 artifact 原文变了，盖在上面的人工修正应何去何从？继续无条件覆盖 → 可能覆盖一个**已过时**的事实（沉淀变污染）；自动失效 → 又退回成会蒸发的东西。正确答案是标记为**待复核**——但当前没有这个状态。

### 1.3 范围边界：三件事被缝成一坨

当前 `annotation_examples` 的读模型同时背了三种职责，绑死在同一套 schema 与读模型里，改任一处牵动全部：

1. **版本管理** = 不可变快照 + 血缘（要的）
2. **质量治理** = 门禁、可信度（必要的）
3. **飞轮自动化** = `effect` 追踪 + auto-publish（用户自认的「设想」，飞轮尚未转起来）

第 3 层是为一个**还不存在**的飞轮造的机器，却长在了核心写路径上——这正是「回写变困难、各种问题」的主要来源。每加一列、每改一次 schema，那堆巨型 LATERAL join 和 auto-publish 的 5 条 reason 都得跟着动。

### 1.4 非目标（本次不做）

明确划界，避免范围蔓延：

- **不动**第 1/2 层：`source_blobs` / `source_bundle_versions` / `releases` 的不可变契约、构建五阶段流水线、LLM 抽取本身。
- **不重设**质量门禁（quality gate）与可信度（trust score）算法——只新增一条 auto-publish reason。
- **不删除**飞轮层（effect 追踪 / auto-publish 自动模式）——只把它从核心写路径**物理拆出并挂开关**，待飞轮真正转起来再启用。
- **不改**用户面 / 内部 ID 的双层命名约定（资料库→资产包→组件→任务→发布→反馈）。
- **不引入**对外部服务的新依赖；漂移检测复用已有的 `content_hash`。

## 2. 设计原则（决策结论）

经评审确认的四条结论：

1. **修正即源（Source，非 Hint）。** 修正是不可变、可寻址、确定性覆盖 LLM 输出的事实。沉淀只有一种形态：源覆盖。`hint` 模式退场为纯 prompt steering，不再被审计为「沉淀」。
2. **必须用 LLM 做抽取，但抽取不进审计基线。** 第 2 层非确定、可重生；可复现的是冻结的 manifest，不是「从源头重推」。修正层（第 3 层）确定性地**盖在** LLM 输出之上。
3. **源漂移 → 修正转「待复核」。** 资料变更时，受影响的修正进入 `pending_review` 状态，构建期**冻结上一已确认值**，不让 LLM 重新发挥。
4. **飞轮层物理拆出 + 真开关。** `effect` 追踪与 auto-publish 自动模式从核心写路径剥离，关闭时核心读模型**完全不 import、不执行**相关 join，而非 UI 层 `if` 包一下的假开关。

## 3. 目标态：三层不可变栈

```
第 1 层  source_version       不可变原料 + parent 链              （已有，不动）
第 2 层  LLM extraction       非确定、可重生、不进审计基线        （已有，不动）
第 3 层  source_corrections   值不可变、sourcePath 寻址、         （本次重建）
                             确定性覆盖、state 机
                             active / pending_review / retired
飞轮层   effect + auto-publish  物理拆出关键路径，挂真开关         （Phase 4）

构建 = 第 2 层抽完 → 第 3 层 active 修正确定性覆盖拍板（无 hint）
                  → pending_review 修正冻结旧值并标记
manifest 冻结三层身份 → 真正「可复现发布内容」+「可审计修正」
```

### 3.1 修正层数据模型

新建独立表 `source_corrections`（**不就地改 `annotation_examples`**，新旧并存至 Phase 3 切换，见 Phase 1）：

| 列 | 类型 | 说明 |
|---|---|---|
| `correction_id` | TEXT PK | 主键 |
| `bundle_id` | TEXT | 资料集 |
| `source_path` | TEXT | **核心锚点**：逻辑路径（normalize 后） |
| `rule_id` | TEXT | 规则 |
| `page_type` | TEXT | 页面类型 |
| `fact_key` | TEXT | 针对 requiredFacts 类修正的具体事实键（可空） |
| `bound_source_hash` | TEXT | **修正所针对源文件的 content_hash**，漂移检测的基准 |
| `state` | TEXT | `active` / `pending_review` / `retired` |
| `correct_value` | JSONB | 覆盖动作（setFacts/removeFacts/replaceSection/...） |
| `component_id` | TEXT NULL | 降级为审计冗余，**不再外键约束、无 CASCADE** |
| `package_id` | TEXT NULL | 同上 |
| `created_by` / `created_at` | — | 审计 |

锚点 = `(bundle_id, source_path, rule_id, fact_key/page_type)`。**移除对 `asset_components` / `asset_packages` 的外键与 CASCADE。**

**唯一约束**：在锚点上建 `UNIQUE`（仅约束 `state <> 'retired'` 的行，用 partial unique index）。保证「同一源文件的同一规则同一事实」**至多一条生效修正**——否则构建期面对两条冲突 active 修正无法裁决。对同一锚点再次修正 = 把旧行置 `retired` 后插新行（见下「不可变性」）。

**不可变性的精确含义**（消除「不可变」与状态机的表面矛盾）：

- `correct_value`（覆盖动作本身）**不可变**。要改正确答案 = 新建一行、旧行 `retire`，绝不原地改值。这与 `source_bundle_versions` 的「重导入走新版本」契约一致。
- `state` 与 `bound_source_hash` 是**生命周期列**，可随状态机转移而变（active⇄pending_review、confirm 更新 hash）。每次转移**必写 `knowledge_event`**，所以「值不可变 + 生命周期可审计」二者不冲突。
- 即：**修正的「内容」不可变，修正的「状态」可追溯地变**。

### 3.2 状态机

```
                    创建（override）
                         │
                         ▼
                     [active] ──────────── retire ──────────▶ [retired]
                       │  ▲
   源文件 content_hash │  │ confirm（复核通过：
   != bound_source_hash│  │ bound_source_hash 更新为新值）
                       ▼  │
                 [pending_review]
```

- **active**：构建时确定性覆盖 LLM 输出。
- **pending_review**：源已漂移。构建时**冻结上一已确认值**（定义见 §3.3）并在 page meta 打 `pending_review` 标记。需人工 `confirm`（接受新源、更新 `bound_source_hash` 回 active）或 `retire`。
- **retired**：不再参与构建，保留审计。

### 3.3 「上一已确认值」的精确定义（待复核机制的命门）

「冻结上一已确认值」必须先回答：**冻的是什么值、从哪取**。否则整个待复核机制无法实现。

漂移发生时，变的是**源文件**，不是修正本身。设：

```
旧源 S0 + 修正 O  →  上次发布里已确认的页面 P0
新源 S1（漂移）+ 修正 O  →  会得到 P1，但 O 是针对 S0 校验过的，P1 可能错
```

**定义**：待复核期间，对该 `source_path` 发布的产物 = **上一个发布版本（release channel 当前指向的 release）manifest 中该 path 冻结的 artifact 内容 P0**，而**不是**用新源重新抽取再套 override 得到的 P1。即冻的是「上次已发布、人已确认的那一页」。

这同时满足两个约束：

- **不蒸发**：修正不丢，P0 是它上次生效的产物。
- **不污染**：不拿一个针对旧源的 override 去硬套已变的新源。

**边界情况**：

1. **该 path 在上一个发布里不存在 P0**（全新路径却已有修正，如源文件改名）：无可冻的旧值。降级策略 = 该修正视为**不适用本次构建**（不应用 override），并标 `pending_review` 待人工确认指向新 path。
2. **跨页一致性风险**（必须正视）：单页冻 P0、其余页用新源 S1，可能造成同一发布内**图谱/索引引用不一致**（P0 提到的实体在 S1 已删）。本方案接受此风险，因为它**可见**（manifest 标了 `pending_review`），优于「静默污染」或「阻断整库发布」。Phase 4 的发布报告需把这种不一致列为**已知债务**，而非伪装成干净发布。

### 3.4 既有回写链（writeback）的去向

现有 `ReviewWritebackSummary` / `annotation.writeback_requested` 事件 / scoped rebuild 编排**不废弃，但语义归位**：

- 旧语义：标注 → 请求回写 → 重建时**喂提示赌 LLM** → 追踪它有没有生效。
- 新语义：标注 = 创建/确认一条 `source_corrections`（**这一步本身就是持久沉淀**）→ 触发 scoped rebuild **确定性套用覆盖层** → `ReviewWritebackSummary` 仍用于串联「修正 → run → release」的审计追踪，但它现在指向的是**不会蒸发的源修正**，而非易朽样例。
- 因此回写不再是「赌一次能否生效」，而是「把已沉淀的源覆盖**重放**到产物」。`injectedBuildCount` 等「注入了几次」的语义随之退化为「重放了几次」，仅作审计。

## 4. 具体实现（How）：五个 Phase

依赖链严格为 `0 → 1 → 2 → 3 → 4`，每个 Phase 可独立验证。

### Phase 0：补防回归测试（安全网）

当前关键路径**零覆盖**。改造前先用真实 PG + 独立 schema 模式（见 `tests/helpers/testEnv.ts`）固定现状：

- `extractStage` 的 `annotationOverrideMatches` / `applyAnnotationOverrides` 按 `sourcePath` 命中并改写 page；
- 回写请求 → scoped build → `ReviewWritebackSummary` 串联；
- `releaseService` 的 auto-publish 5 条 eligibility（含按 `artifactId` 的 trust 下降检测）。

**验证**：测试全绿。**风险**：极低（只加测试）。

### Phase 1：修正迁成 source 覆盖层（解除 CASCADE）

- 新增 `source_corrections` 表（结构见 §3.1），`CREATE TABLE IF NOT EXISTS` + `ALTER ... ADD COLUMN IF NOT EXISTS` + 数据回填迁移，二次启动幂等（遵循 `db.ts:migrate()` 既有约定，不改既有 CREATE）。
- 回填 override：从现有 `annotation_examples` 取 `apply_mode = 'override'` 的记录，按 `contextSnapshot` 推导 `source_path`（复用 `annotationOverrideFromExample` 的 sourcePath 推导逻辑），`bound_source_hash` 取对应源文件当前 hash，`state = active`。
- **现有 `hint` 记录的去向**（必须明确，否则丢数据）：`hint` 不进 `source_corrections`（按决策①它不再是「沉淀」）。但**不静默丢弃**——保留原 `annotation_examples` 表只读一段过渡期，或导出为审计归档，并在迁移日志中记录被降级的 hint 条数。退役时机另行决定。
- `source_corrections` 的 `component_id` / `package_id` 为可空审计列、无外键、无 CASCADE。
- **回滚**：迁移失败时 `ROLLBACK`；`source_corrections` 是新表，回滚不影响既有 `annotation_examples`，旧构建路径在 Phase 3 切换前保持可用。

**验证**：rebuild 后 `source_corrections` 记录不被连坐删除（对照实验：旧 `annotation_examples` 会被删）。**风险**：中（迁移，但 additive；新旧并存直到 Phase 3 切换）。

### Phase 2：源漂移 → 修正自动转 pending_review

- 在 `sourceBundleService.importDirectoryAsVersion` 内，对每个 `logical_path` 的 `content_hash` 做 diff。
- 凡有 `active` 修正、且该 path 的新 `content_hash != bound_source_hash` → 该修正 `state` 翻成 `pending_review`，写 `knowledge_event` 审计。
- 提供 `confirm`（复核通过：`bound_source_hash` 更新为新值、`state` 回 `active`）与 `retire` 两个操作 + 路由（`denyRole("viewer")`）。

**验证**：改资料 → 受影响修正变 `pending_review`。**风险**：低。

### Phase 3：构建把覆盖层当源盖在 LLM 之上（override-only + 冻结待复核）

- `extractStage` 改为读 `source_corrections` 作为权威覆盖层：
  - `state = active` → 确定性覆盖；
  - `state = pending_review` → **冻结上一已确认值**（取上个发布 manifest 中该 path 的 artifact，定义见 §3.3）并在 page meta 打 `pending_review` 标记，不让 LLM 重新发挥；处理 §3.3 的两个边界情况（无 P0 → 不应用 override 并标待复核；跨页不一致 → 记为已知债务）；
- `hint` 不再作为「持久沉淀」路径（可保留为纯 prompt steering，但不进 `source_corrections`）。
- `loadAnnotationExamplesForPrompt` 改为按 `sourcePath` 加载本次 build 涉及文件的修正。

**验证**：待复核 artifact 构建产物 = 旧值 + 标记。**风险**：中（动 `extractStage`）。

### Phase 4：发布标记待复核债 + 物理拆飞轮挂真开关

- **(A) 带债发布、债务可见**：`releaseService` 的 `AutoPublishCheck` 新增 reason `has_pending_review_corrections`。发布**可带「待复核债务」出门**，但 manifest 明确记录哪些 artifact 含 `pending_review` 覆盖。语义是「带债发布、债务可见」，**而非「有待复核就阻断整次发布」**（避免一条小修正卡死整库发布）。
- **(B) 物理拆飞轮**：把 `effect` 追踪那段巨型 LATERAL join 从 `listAnnotationExamples` 拆出，移入独立 `flywheelMetricsService`，仅在真开关（如 `KH_FLYWHEEL_METRICS`）开启时调用；关闭时核心读模型完全不 import、不执行该 join。auto-publish 自动模式同样受同一开关控制。

**验证**：关开关 → 巨型 join 不执行，核心读模型无该依赖。**风险**：低。

## 5. 目标结果（What we get）

| 维度 | 现状 | 重构后 |
|---|---|---|
| **持久化** | 修正被 CASCADE 连坐删除 | 修正锚定 `source_path`，重建不删 |
| **寻址** | `component_id`（跨构建不稳） | `source_path`（稳定，override 本就在用） |
| **生效方式** | 每次构建重喂 LLM「赌」 | active 修正确定性覆盖，LLM 无发言权 |
| **源漂移** | 静默失效 / 静默污染 | 转 `pending_review`，冻旧值 + 可见标记 |
| **hint/override** | 边界不清，用户每次纠结 | 沉淀只有一种：源覆盖；hint 退为纯提示 |
| **回写语义** | 喂提示「赌」LLM 这次生效（§3.4） | 把已沉淀的源覆盖**确定性重放**到产物 |
| **发布** | 审计的是会过期的修正 | 带债可见发布（债务列入 manifest）+ 冻结三层身份 |
| **飞轮层** | 缝进核心写路径，改一处动全身 | 物理拆出 + 真开关，可整块关闭 |
| **关键路径测试** | 零覆盖 | 覆盖 / 回写 / 发布均有防回归 |

### 5.1 一句话结论

最初的问题是「版本管理是不是设计得过于复杂」。答案：**不是复杂，是放错位置**——

- 把**要沉淀的源**（第 3 层）建成了会蒸发的提示 → 真债，必修；
- 把**没成型的飞轮**（effect / auto-publish）缝进核心写路径 → 早产，该拆。

两个归位后，版本管理从「缝合怪」变回三层各自不可变、各自能单独推理的栈。**「可审计、可管理、可发布」三个词到那时才真正成立**——因为现在的「可审计」审计的是会过期的修正，「可管理」管的是缝死的耦合。

## 6. 待确认项

> 已拍板（不再讨论）：
> - 待复核期间构建产物 = **冻结上一已确认值 + 标记**，*带债发布、债务可见*（非阻断整库发布）。

仍待确认：

1. **Phase 0 遇到现有 bug**：写测试基线时若暴露现有 bug，是顺手修，还是只记录、留到对应重构 Phase 再处理。
2. **跨页一致性容忍度（§3.3 边界 2）**：待复核单页冻 P0、邻页用新源，可能产生图谱/索引引用不一致。方案默认「可见即可接受」。是否需要更强策略（如：一旦某 path 待复核，连带把引用它的页也标待复核）？默认否，按需升级。
3. **hint 历史数据退役时机（Phase 1）**：被降级的 `hint` 记录过渡期保留多久、是否需要导出归档格式。
4. **scoped rebuild 的旧值来源**：scoped 重建只跑部分文件时，「上一已确认值」仍取自上个**完整发布**的 manifest（而非上个 scoped run）——确认这一取值口径。
